# ADR-0015: Alembic Migration Authority

**Status:** Accepted  
**Date:** 2026-09-21  
**Scope:** Project-owned database schemas and new application scaffolding

## Decision

Use Alembic as the migration authority for project-owned application and shared
platform schemas, complementing [SQLAlchemy database access](./0014-python-database-access-and-api-models.md).
Supabase continues to provide PostgreSQL, Auth and storage. Supabase-managed
internal schemas are excluded from project migration ownership and model diffing.
Only one migration runner owns any given database object.

Generate candidate migrations from SQLAlchemy metadata where useful, then review
and test them. Add explicit SQL or operations for data transformations, RLS,
permissions, functions, triggers and changes not correctly inferred. Model edits
alone never alter deployed schemas. Applied migrations are deployment artifacts;
application startup does not substitute automatic table creation for migration.

Adopt the existing repository-owned SQL definitions deliberately. Establish and
verify a baseline for each supported existing development database; no production
system is currently deployed. This decision does not authorize dropping existing
data or falsely marking unapplied definitions as applied. Do not run Supabase and
Alembic migration histories against the same owned objects after their cutover.

Align local bootstrap/reset, seed ordering, CI and release commands with Alembic.
The existing SQL composition script and migration sources remain in place until
that transition is implemented and verified. Supabase assets such as functions
and environment configuration may still require their existing tooling.

Application migration ownership, version-table placement, cross-owner ordering
and deployment coordination are the next architecture decisions. Alembic must
preserve [application silo boundaries](./0003-application-silo-architecture.md).

## Consequences

- Scaffold: provide Alembic configuration, explicit owned-schema filtering,
  migration templates and disposable-database verification once proven.
- Verification: cover empty-database creation, supported upgrade paths, schema/model
  agreement, RLS and grants; autogenerated diffs do not verify all these properties.
- Shared UI: no impact.
- Agent context: update database-composition guidance when replacement commands
  actually exist; the current composition check remains valid for current assets.
- Documentation: builder direction and Leave tracker identify transition work.
- ADR impact: additive; accepted ADRs remain immutable.
- Planning only; no migration execution, dependency installation or data change.
