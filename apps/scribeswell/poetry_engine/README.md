# Psalm Poetry Engine

A local research pipeline for comparing reviewable Afrikaans Psalm drafts. It does
not produce authoritative Bible translations or establish singability. The first
real source slice is Psalm 23; the code accepts other Psalms.

The Scribeswell database has been repaired separately. See
[the repair record](../docs/data-repair.md). The experiment reads pinned original
source files to retain original linguistic identifiers, rather than using database
surrogate IDs as scholarly source IDs.

## Install and verify

```bash
cd apps/scribeswell/poetry_engine
uv sync --extra sources --extra dev
uv run pytest
uv run ruff check src tests
uv run ruff format --check src tests
uv run mypy src --ignore-missing-imports
```

The lockfile pins the tested dependencies. `sources` installs Text-Fabric and pypdf;
core schemas/generation require only Pydantic. No API server or database is required.

## Source data and Git

`data/raw/morphhb/` and `data/raw/bhsa-2021/` are intended for Git. They contain pinned
source files, checksums and attribution/license notices. The selected raw files
are approximately 57 MiB before Git compression. MorphHB is CC BY 4.0; BHSA data is
CC BY-NC 4.0. This project is free and noncommercial. See
[THIRD_PARTY_DATA.md](THIRD_PARTY_DATA.md) and [data_sources.yaml](data_sources.yaml).

Only binary Text-Fabric caches, environments, intermediate PDF full text and working
runs are ignored. Explicitly selected research artifacts can be kept under
`data/samples/` or `docs/results/`. The supplied PDF rights remain unverified;
noncommercial use alone does not establish redistribution rights for them.

To fetch a fresh pinned BHSA source directory:

```bash
uv run psalm-engine fetch-bhsa --revision 4db00e2157915495e1a4d3d57e41223df24775da --output data/raw/bhsa-fresh
```

The loader checks every declared source feature against its manifest. Fetching an
existing output directory fails rather than mixing versions. All downstream commands
use local data and fail if required evidence is missing.

## Build the real representation

```bash
uv run psalm-engine build-representation --psalm 23 --morphhb data/raw/morphhb/Ps.xml --morphhb-revision 3d15126fb1ef74867fc1434be1942e837932691f --bhsa data/raw/bhsa-2021 --annotations data/annotations/psalm-023.proposed.jsonl --output runs/psalm-023.json
uv run psalm-engine validate-representation runs/psalm-023.json
```

This imports both sources, aligns tokens, and writes the representation plus a separate
`.alignment.json` report. Separate import/align CLI commands are intentionally combined
so they operate on exactly the same inputs. Source facts, structures and raw grammatical
features remain distinct from interpretive claims. The committed sample includes a
pending PDF principle as well; no human approval is inferred.

Psalm 23 contains 57 MorphHB words and 69 BHSA tokens. Alignment accounts for every
one, with zero unmatched groups in this slice. This is consonantal agreement, not
proof that vocalization or interpretation is equivalent. The BHSA article node 313945
has an empty written form; it is explicitly retained as `source_empty`. Other blank
source surfaces fail validation. Alternative MorphHB notes are retained as metadata,
not silently inserted into the main-text token stream.

## Prepare comparable translation requests

Replace `PROVIDER` and `MODEL` with actual identifiers chosen for the experiment:

```bash
uv run psalm-engine experiment --representation runs/psalm-023.json --provider PROVIDER --model MODEL --conditions A B C --settings '{}' --output runs
```

The printed directory contains exact request files and hashes, source representation,
prompt version and code provenance. No translation is generated by preparation.

| Condition | Evidence supplied |
| --- | --- |
| A | Hebrew text and the common translation brief |
| B | A plus MorphHB token annotations |
| C | Hebrew plus canonical representation, MorphHB and BHSA |
| D | C plus human-approved PDF principles with page provenance |

Language, mode and model settings are identical within a run. Rejected annotations
are excluded. Pending/disputed non-PDF interpretations retain their explicit status.
PDF-derived material is excluded from C. D fails until an approved principle exists.
The initial run is descriptive; it is not a statistical demonstration of improvement.

## Generate through your chosen provider

The provider-neutral `TranslationGenerator` interface has a concrete `CommandGenerator`.
Configure an executable that reads one `GenerationRequest` JSON from stdin, calls your
provider and prints one `GenerationResponse` JSON to stdout. Keep API credentials in
that executable's environment. The request includes system instructions, evidence,
settings and the exact response JSON schema. Echo the request ID, provider, model,
language, mode and settings; never invent usage statistics. Notes may only cite IDs
in `input.allowed_evidence_refs`.

```bash
uv run psalm-engine run runs/EXPERIMENT_DIRECTORY --runner 'python /path/to/your_provider_runner.py'
```

Alternatively pass `--runner` to `experiment` to prepare and execute together. No
provider-specific SDK or credential is selected by this prototype. Choosing and
configuring the real provider is still required before generating research drafts.
The runner is invoked without a shell. Errors, malformed responses, model/settings
mismatches, fabricated evidence references, or mixed synthetic/real output fail the
run. Failed attempts retain completed condition artifacts and a failure record. They
cannot be silently rerun over the same directory; prepare a new attempt.

Successful generation writes responses, latency, usage when reported, `comparison.md`
and `evaluation-template.json`. Synthetic outputs are only used in tests and are
labelled as such. Supported modes are `literal`, `poetic` and
`song-oriented-without-melody`. No melody-constrained mode is implemented.

## Review research and evaluate drafts

```bash
uv run psalm-engine ingest-pdf resources/psalms-23.pdf --output data/interim/psalm-23-pages.json
uv run psalm-engine validate-annotations data/annotations/psalm-023.proposed.jsonl
uv run psalm-engine validate-annotations data/annotations/principles.proposed.jsonl --csv data/interim/principles.csv
```

Read [the annotation guide](docs/annotation-guide.md) before approving a claim. Rebuild
with `--principles YOUR_REVIEWED.jsonl --pdf-evidence data/interim/psalm-23-pages.json`
to include its provenance. Page extraction does not approve research claims and does
not transmit full PDF text to a model.

After generation, fill a copy of the evaluation template using
[the evaluation guide](docs/evaluation-guide.md), then run:

```bash
uv run psalm-engine evaluate runs/EXPERIMENT_DIRECTORY --evaluations completed-evaluations.json
```

Each evaluation is a new artifact. All twelve categories remain available alongside
a weighted score and human revisions. No automatic quality score is fabricated.

## Scope and current limits

See [research-plan.md](docs/research-plan.md) for the assessment, architecture decisions,
phases, research questions and first-slice acceptance criteria. See
[canonical-representation.md](docs/canonical-representation.md) for schema semantics.

Source loading, alignment, schema validation, PDF extraction, request preparation,
provider-runner orchestration, comparison reports and rubric persistence are implemented.
Actual provider-generated drafts, named human annotation review and quality evaluation
are still required to complete the research milestone. No API/UI, automatic poetic
analysis, trained model, embeddings, or claim of general translation improvement is
part of this first slice.
