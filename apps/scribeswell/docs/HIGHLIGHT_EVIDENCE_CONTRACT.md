# Highlight evidence comparison

Implemented: `backend/highlight_evidence.py` is a pure comparison primitive. It is not connected to the public reader or private Notes API. It neither publishes sources nor grants permission to save anchors.

`observe_verse(publication, words)` takes one caller-trusted current observation and complete ordered verse words. The publication supplies version 1, ready status, source/catalogue/versification/tokenization labels, a nonzero canonical source revision UUID, canonical Hebrew book/chapter/verse, exact verse digest and full observed word ID inventory. Words supply contiguous integer positions, decimal bigint IDs and exact Hebrew surfaces. Digest encoding is the existing `scribeswell.verse_tokens.v1` encoding. The result is a new ready observation with token count, or only `{version: 1, status: unavailable}` on invalid/mismatching input. It never returns text surfaces.

`segment_status(segment, evidence)` validates a saved segment's identity, source revision, full-verse digest, inclusive start/end positions and selected observed IDs. Invalid saved data raises the fixed `highlight_evidence.segment_invalid` error. Unavailable or malformed current evidence returns unavailable. A coherent current observation with changed source/catalogue/versification/tokenization, verse, digest or missing range returns needs_review. Otherwise it returns valid. Revision and database ID changes alone do not invalidate exact unchanged verse tokens. Inputs are never rewritten.

The accepted shape is internal, not a new wire DTO. Positions are bounded to 512 tokens, Hebrew source books, chapter 1–150 and verse 1–176; complete catalogue eligibility and publication authority remain adapter responsibilities. IDs are canonical positive decimal PostgreSQL bigint strings. Each selected segment carries exactly one ID per selected position; current observations carry the complete distinct inventory.

Still proposed: a protected immutable publication manifest and activation transition, fenced audit/import integration, a bounded read-only repeatable snapshot supplying publication and words together, canonical reference DTO mapping, trusted base-revision preservation, and current-proof validation before new/repaired anchor writes. A caller must not accept a new anchor from browser-supplied proof or from this primitive alone. Publication readiness cannot be inferred from a matching digest, closed controller attempt, or historical audit candidate. No source text matching, fuzzy relocation, actor/Access inference or organization prerequisite is introduced.

Tests use synthetic observations only. Native database, owner-service, public browser, physical selection-device and release qualification remain pending. No migrations or runtime behavior are changed by this slice.

## Immutable manifest candidate assembly

Implemented `backend/corpus_manifest.py` requalifies exact source bytes through the existing full-source qualifier, then binds the ordered complete verse digest inventory and externally observed IDs to canonical source revision, executor actor, attempt and positive generation. Expected attempt/generation must match. Missing/extra verses, wrong token counts, noncanonical/out-of-range IDs and any globally repeated ID are rejected with `corpus_manifest.invalid`. Frozen records and tuples retain no mutable input aliases or text surfaces. This is an internal candidate model, not a wire format or durable manifest.

The candidate always reports `publication: false`. It does not verify that supplied IDs identify matching database surfaces, that the expected attempt is current, or that the executor has publication authority. The future protected audit must read actual text/IDs under the same fence and bind this result to its controlled transition; passing arbitrary external observation data through the assembler never establishes readiness. Existing historical audit receipts remain non-authoritative. Immutable database storage, current publication pointers, release adoption and ready reader snapshots remain pending.

## Importer transaction binding — implemented, activation deferred

The existing `tools/py/import_bible.py` accepts an optional immutable `ImportBinding`. CLI equivalents are the all-or-none options `--source-id`, `--attempt-id`, `--generation` and `--expected-source-sha256`. These identify an already authorized owner attempt; they neither create it nor authorize a caller. Source IDs use the existing label grammar, attempt IDs canonical nonzero UUIDs, generations positive decimal bigint strings, and checksums lowercase SHA-256.

Fenced `run()` reads at most 32 MiB plus one byte once, checks the approved checksum, rejects duplicate JSON keys, requires all 39 known books and reuses the complete source qualifier before selecting any `--book` repair. Its transient `import-preflight-v1` labels are local validation placeholders; the discarded source candidate establishes no publication identity. The source qualifier enforces chapter/verse/token and UTF-8 field-size bounds and emits safe fixed errors. Book seeding and each existing chapter-write transaction call the fixed parameterized `scribeswell.bind_corpus_write` routine on that same transaction's connection before any upsert. A rejected binding aborts that transaction and stops the run; earlier committed chapters remain committed. Direct fenced write entry points cannot skip the run's source qualification. The final report uses the original bytes' checksum, even if the source file changes during execution. Verify-only and dry-run do not bind or write.

Legacy invocation remains available while the existing database enforcement switch is off. No grant or enforcement switch changes here. With enforcement enabled the database rejects unbound writes; a CLI flag is not the security boundary. Controlled activation still requires restricted execute grants, native tests of direct alternate writers/pool reuse/rollback, and migration/previous-writer coordination. Import success or one-book repair is never source publication. Protected closed-attempt auditing, durable manifest staging, short activation CAS/outcome and coherent reader proof remain pending.

## Closed-attempt audit adapter — implemented, durable publication pending

`backend/closed_corpus_audit.py::audit_closed_attempt(connection, command_raw, source_raw, source_revision=...)` is the controlled owner auditor. It accepts the original strict `corpus.seal` command and exact full approved source bytes, not claimed audit JSON or an external manifest. The revision is a stable canonical nonzero UUID selected by the owner for the planned staging operation. It reuses source qualification before SQL, reconciles the original closed receipt through the existing current-authority lookup, then checks current enforcement, closed epoch/attempt, source/checksum/identity and enabled principal/seal authority in the same read-only repeatable snapshot as the complete actual corpus comparison. Actual word IDs come from that scan. Only successful snapshot exit and complete immutable assembly return a `ManifestCandidate`; it still reports publication false.

The existing source audit visibility and full inventory/token/digest checks are reused. No business coordination locks span the scan. A concurrent owner recovery can retire the observed attempt; later activation must reject the stale tuple. Receipt reconciliation uses the tuple factory required by the existing controller; the audit uses dictionary rows. The caller's original factory is restored across both phases, including lookup and snapshot failures. Fixed typed errors disclose neither source text nor driver context. The 60-second executing deadline covers source qualification, receipt reconciliation, scan and assembly; finite statement/lock/idle waits remain. This adapter cannot interrupt arbitrary network/transport stalls itself: the existing controlled caller must supply execution containment. It opens no connections and installs no supervisor.

The adapter requires explicitly prepared read grants over the app-owned control/epoch/attempt/principal/authority metadata and corpus, plus the existing lookup EXECUTE grant, under the restricted `scribeswell_corpus_operator` principal. No such new grants are shipped or applied here. Missing preparation fails closed. Controlled schema/role DDL must remain stable during qualification. Application-side doubles establish orchestration and exact comparison only; actual restricted-role visibility, fence exclusion, recovery races and transport budgets require the final native integration.

### Durable attestation and activation contract — proposed implementation

The trust boundary is the controlled Scribeswell owner auditor runtime. A frozen candidate, closed receipt, historical audit file, matching hash or shape-valid SQL payload is never independently proof of actual correspondence. Only that trusted runtime may feed the protected staging/completion routines; no browser or general external request may submit claimed audited manifests. The database protects restricted writes, immutable stage/completion records, structural completeness and final current-state CAS; it does not claim to independently rerun the Python full-source audit.

Retain the existing updating/closed epoch and attempt enums. A separate publication pointer is usable only while enforcement is enabled and its completed manifest belongs to the current closed epoch/attempt. Begin/recover therefore makes old proof unavailable without deleting history or changing `corpus.seal` semantics. Recovery advances generation and retires prior attempts, invalidating pending activation.

Use immutable stage headers, ordered verse rows and a separate immutable completion record. Stage binds source/revision/attempt/generation/approved checksum, source labels, executor and auditor contract version. Batches contain at most 1,000 verses; existing audit maxima of 50,000 verses and 1,000,000 tokens apply, with a 64 MiB encoded-manifest ceiling. Completeness requires the full qualified supported inventory, exact ordered IDs/counts and manifest digest, never a partial `--book` output. Abandoned or incomplete stages cannot activate and are retained for owner investigation; no automatic cleanup policy is introduced.

The planned manifest digest is SHA-256 over compact UTF-8 JSON without BOM/newline/normalization: `["scribeswell.manifest.v1", auditor_contract_version, source_id, catalogue_version, versification_id, tokenization_version, source_sha256, source_revision, executor_actor_id, attempt_id, generation_decimal_string, [[canonical_book, chapter, verse, verse_token_digest, [ordered_decimal_word_ids]], ...]]`. Verse order is the existing full-source qualifier's canonical book/chapter/verse order. This encoding is a concrete design, not yet implemented or accepted from external callers.

A source revision UUID is globally unique across all sources, attempts and stages. Its first immutable header permanently binds one complete manifest identity, including source/attempt/generation, auditor contract version, executor, declared digest/counts and ordered inventory; reuse with any difference conflicts. There is no revision rebinding or overwrite after recovery.

Stage creation, batch append and completion are separate acknowledged writes. Each has a caller-retained operation UUID under the existing database-login operation namespace, with command/version and the complete semantic input recorded in its immutable outcome. Current authority gates lookups and replays. An identical committed retry returns its original receipt; the same operation UUID with different input conflicts. Explicit lookup reconciles a lost acknowledgement before a new operation is attempted. No stage or batch receipt claims completion or publication.

Stage creation also has the globally unique revision key: another operation may only return an already identical header, never alter it. Batch identity is `(source_revision, zero_based_batch_index)` with a declared first verse ordinal and the complete canonical ordered rows. Accept only the next contiguous batch within declared bounds; an already committed identical batch returns its original identity, while changed rows/order/ordinal conflict. Completion binds the revision, auditor contract version, full manifest digest and counts after all declared batches are present; there is one immutable completion per revision. New writes recheck the current enforced closed attempt. After recovery, current-authorized lookup or exact committed replay may report historical acknowledgements without changing any state; missing old writes cannot finish the retired stage. Activation independently verifies the immutable auditor-version/digest/header/completion binding.

Final activation is a short owner transaction in the existing lock order: current principal/explicit publication authority, enforcement/control, epoch and attempt, then the completed immutable stage. Recheck exact identities, closed state and completion digest/counts, atomically write active publication plus immutable operation outcome with server UTC/actor attribution, then acknowledge after commit. The explicit publication capability/routine and records still require a forward owned migration and coordinated profile/grant qualification; they are not provided by this audit adapter.

Activation retries reconcile the same semantic operation under current authority. A matching committed outcome returns its original revision even if later retired; it never reactivates that revision. Reused operation identity with different semantics conflicts. Unknown completion requires original-operation lookup before restart. No source mutation or automatic rollback/downgrade is part of publication recovery. Additive migration adoption, generated references/profile compatibility, source-owner admission and release activation remain final-phase prerequisites.
