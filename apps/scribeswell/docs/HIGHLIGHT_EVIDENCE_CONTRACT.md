# Highlight evidence comparison

Implemented: `backend/highlight_evidence.py` is a pure comparison primitive. It is not connected to the public reader or private Notes API. It neither publishes sources nor grants permission to save anchors.

`observe_verse(publication, words)` takes one caller-trusted current observation and complete ordered verse words. The publication supplies version 1, ready status, source/catalogue/versification/tokenization labels, a nonzero canonical source revision UUID, canonical Hebrew book/chapter/verse, exact verse digest and full observed word ID inventory. Words supply contiguous integer positions, decimal bigint IDs and exact Hebrew surfaces. Digest encoding is the existing `scribeswell.verse_tokens.v1` encoding. The result is a new ready observation with token count, or only `{version: 1, status: unavailable}` on invalid/mismatching input. It never returns text surfaces.

`segment_status(segment, evidence)` validates a saved segment's identity, source revision, full-verse digest, inclusive start/end positions and selected observed IDs. Invalid saved data raises the fixed `highlight_evidence.segment_invalid` error. Unavailable or malformed current evidence returns unavailable. A coherent current observation with changed source/catalogue/versification/tokenization, verse, digest or missing range returns needs_review. Otherwise it returns valid. Revision and database ID changes alone do not invalidate exact unchanged verse tokens. Inputs are never rewritten.

The accepted shape is internal, not a new wire DTO. Positions are bounded to 512 tokens, Hebrew source books, chapter 1–150 and verse 1–176; complete catalogue eligibility and publication authority remain adapter responsibilities. IDs are canonical positive decimal PostgreSQL bigint strings. Each selected segment carries exactly one ID per selected position; current observations carry the complete distinct inventory.

Still proposed: a protected immutable publication manifest and activation transition, fenced audit/import integration, a bounded read-only repeatable snapshot supplying publication and words together, canonical reference DTO mapping, trusted base-revision preservation, and current-proof validation before new/repaired anchor writes. A caller must not accept a new anchor from browser-supplied proof or from this primitive alone. Publication readiness cannot be inferred from a matching digest, closed controller attempt, or historical audit candidate. No source text matching, fuzzy relocation, actor/Access inference or organization prerequisite is introduced.

Tests use synthetic observations only. Native database, owner-service, public browser, physical selection-device and release qualification remain pending. No migrations or runtime behavior are changed by this slice.

## Immutable manifest candidate assembly

Implemented `backend/corpus_manifest.py` requalifies exact source bytes through the existing full-source qualifier, then binds the ordered complete verse digest inventory and externally observed IDs to canonical source revision, executor actor, attempt and positive generation. Expected attempt/generation must match. Missing/extra verses, wrong token counts, noncanonical/out-of-range IDs and any globally repeated ID are rejected with `corpus_manifest.invalid`. Frozen records and tuples retain no mutable input aliases or text surfaces. This is an internal candidate model, not a wire format or durable manifest.

The candidate always reports `publication: false`. It does not verify that supplied IDs identify matching database surfaces, that the expected attempt is current, or that the executor has publication authority. The future protected audit must read actual text/IDs under the same fence and bind this result to its controlled transition; passing arbitrary external observation data through the assembler never establishes readiness. Existing historical audit receipts remain non-authoritative. Immutable database storage, current publication pointers, release adoption and ready reader snapshots remain pending.
